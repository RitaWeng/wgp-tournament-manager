# WGP 比賽管理系統

專為 WGP GiveMe5 棋賽設計的桌次管理工具，支援瑞士制配對、輔分計算、多輪次管理，並可匯出 Excel 成績表。

線上版：https://ritaweng.github.io/wgp-tournament-manager/
---

## 功能特色

### 賽制
- **瑞士制配對**：採用分組回溯法（對應 VBA Sub VS 邏輯），依總分分組後進行組內回溯搜尋，確保每輪配對最優化
- **輪動平衡**（Float Balance）：計算每位選手歷輪「輪高/輪低」次數，避免重複遭遇強弱懸殊的對手
- 奇數人時自動安排**輪空**，輪空選手自動獲得勝分
- 先後手（黑/白）依當前輪次、歷輪黑方次數自動平衡分配

### 配對流程
1. **抽籤**（僅限第 1 輪）：隨機洗牌重排籤號，執行前彈出確認視窗
2. **抓對**：依當前輪次產生桌次表；已算分的輪次鎖定後不可重複抓對
3. **登錄結果**：點選勝方即可記錄；已算分輪次以唯讀標籤顯示
4. **算分**：計算總分、三項輔分、並列名次，完成後鎖定本輪
5. 進入下一輪，重複步驟 2–4

### 輔分規則
| 輔分 | 說明 |
|------|------|
| 輔分一 | 所遇對手之總分和 |
| 輔分二 | 所負對手之總分和 |
| 輔分三 | 在總分、輔分一、輔分二均相同時，計算彼此直接對戰勝負（勝 +1） |

名次支援並列（1, 1, 3, 4, 4, 6…）。

### 鎖定與解鎖
- 每輪算分後自動**鎖定**，桌次表與成績進入唯讀模式
- 如需修改，可點擊「🔓 解除鎖定」，確認後重新開放結果輸入，再按「算分」重新計算

### 狀態儲存
- 所有狀態自動同步至瀏覽器 **localStorage**，關閉後重開可自動恢復
- **下載狀態**：將完整狀態匯出為 `.json` 備份檔
- **上傳狀態**：載入 `.json` 備份以還原任意時間點的賽況

### 資料匯入／匯出
- **上傳隊伍表**：支援 `.xlsx` / `.xls`，自動辨識籤號（`籤號`、`No`、`編號`…）與隊伍名稱（`隊伍`、`name`、`team`…）欄位
- **下載選手成績**：匯出含所有輪次分數、對手、輔分、名次的 Excel（多分頁）
- **下載桌次表**：匯出當前選定輪次的桌次 Excel

### 介面
- 左右**分割視窗**：左側為排行榜、右側為桌次表，可拖動分隔線調整比例（30%–70%）
- **排行榜雙視圖**：
  - 「**緊湊**」＝領先三隊突顯卡＋列表，每輪以**對戰方塊**顯示對手縮寫與勝負
    （勝＝實心綠、負＝淺紅、輪空勝＝灰、進行中＝藍虛線框並直接顯示本輪對手、未開始＝空框），
    滑鼠移上方塊顯示完整對戰資訊（如「R2 勝 vs 7. 台中一中」）
  - 「**詳細**」＝總分、三項輔分與每輪分數的完整表格，每輪格 hover 顯示對手隊名
  - 縮寫規則：取隊名前兩字；5 字以上再附隊名中最後一個英文字母（「建國中學A」→「建國A」）
- 輪次進度指示器：已完成（✓ 綠色）、進行中（琥珀色、脈動）、未開始（空心）
- 右側桌次表以輪次頁籤（R1、R2⋯）切換查看任意輪次，已完成輪次標示 ✓
- **流程引導提示列**：依目前狀態自動顯示下一步操作提示
- 「輔分說明」彈窗隨時查閱輔分定義
- **多主題**：light / dark / paper / navy 即時切換，選擇寫入 localStorage
- **手機 RWD**：雙欄改堆疊、設定列改 2 欄、桌次配對改上下排版，支援 iOS Safari `100dvh` 視窗
- **投影模式**：名次表與當前輪次桌次表獨立投影視窗，投影按鈕在手機隱藏
  - 桌次表投影：**兩隊上下堆疊**、桌號跨兩行置中（暖琥珀／冷藍區分奇偶桌）、籤號純數字對齊；
    依桌數自動選欄數、字級放大吃滿整個畫面，長隊名自動縮字（中文隊名以最大字級完整顯示為優先）
  - 投影專用**亮／暗主題切換**（預設深色、記憶選擇，只影響投影畫面，操作介面維持原主題）；
    色帶、邊框與字重為投影機做對比強化

### 設定的修改限制
比賽一旦開始（任一輪已抓對或已算分），系統依「不抹掉已紀錄資料」原則鎖定設定欄位：

| 欄位 | 開賽後 |
|------|--------|
| 參賽隊伍 | 唯讀（鎖定） |
| 勝方得分 | 唯讀（鎖定） |
| 輪數 | **可下調、不可上調**；下限 = max(目前輪次, 已抓對輪次, 已計分輪次)，避免「3 隊 4 輪」之類設定卡死無出口 |
| 已算分輪次的結果 | 唯讀；要修改點該輪的「🔓 解除鎖定」 |

完整復原回初始狀態請按「重設」 — 會清空所有桌次、計分與選手資料（無法復原）。

## 線上成績回報：比賽日操作指南

讓各桌裁判用手機回報該桌勝負，主控端自動彙整（**選用功能**，不開也完全不影響現有流程；
架構與安全設計見[下方章節](#線上成績回報選用)）。後端網址見 `docs/online-score-reporting-ops.md`（維運手冊）。

### 賽前（主控電腦）

1. 照常上傳隊伍表、設好輪數。
2. 按「**線上回報**」→ 貼上後端網址與**建立金鑰**（部署時設定的 SETUP_KEY，防止陌生人
   對後端灌垃圾資料）→「**建立線上賽事**」。兩者輸入一次會記住。
   - ✔ 面板顯示「已連線」綠燈。
3. 「**列印 QR 卡**」→ 印出各桌 QR 卡，**整疊交給計分台保管**（不上桌、不給裁判帶走）。
4. 裁判報到時到計分台，工作人員當面讓裁判掃自己桌的 QR → 手機顯示「等待桌次發佈」→ 卡收回。
   - ✔ 面板「各桌狀態」該桌變「在線」。整天只需掃這一次；手機沒電換機回計分台重掃即可。

### 每一輪

5. 「抓對」之後按「**發佈桌次**」→ 裁判手機約 10 秒內自動顯示本桌對局。
   - 同一輪需要**重新抓對**時，重抓後再按一次「發佈桌次」即可，之後的裁判回報照常採計
     （重發前收到的舊桌次回報自動作廢；v1.4.5 起支援）。
6. 裁判逐組點選 A~E 五組勝方（該組加賽才分出的點「加賽」）→ 送出前確認 → 送出。
   - ✔ 主控端桌卡自動打勾、標「**裁判**」與五組比數（如 3:2，滑鼠移上去看各組明細）。
7. 沒掃碼或斷網的桌照常**手動點選登錄**，兩者可混用。
8. 到齊後照常「**算分**」→ 該輪自動鎖定，裁判端顯示 🔒、不能再改。

### 裁判更正與衝突

- 鎖定前裁判可自行更正：**勝方不變**（如補記加賽）→ 主控端靜默帶入；
  **勝方翻盤** → 主控端跳醒目確認窗，由操作者決定「採計」或「維持現狀」。
- 按「維持現狀」後，裁判手機會顯示「**更正未被計分台採計，請至計分台說明**」。
- 同桌 device 變化會在「各桌狀態」標 ⚠（token 外洩偵測，詳見安全章節）。

### 賽後

9. 按「**結束線上賽事**」→ 伺服器資料立即刪除、所有 QR 卡失效（忘了按也有 7 天自動清除）。
10. 照常匯出 Excel——桌次表會多出 A~E 各組勝負與組數欄。

**後端掛掉怎麼辦**：主控端顯示「連線異常」，全部退回手動點選登錄，比賽照常進行，資料模型完全相同。

## 部署

線上版透過 `gh-pages` 套件自動推送 build 後的 `dist/` 到 `gh-pages` 分支。本專案分**正式**與**測試**兩個環境，共用同一個 GitHub Pages 站點，以子路徑區分：

| 環境 | 來源分支 | 部署指令 | 網址 |
|------|----------|----------|------|
| 正式 | `master`  | `npm run deploy`         | `https://ritaweng.github.io/wgp-tournament-manager/` |
| 測試 | `develop` | `npm run deploy:preview` | `https://ritaweng.github.io/wgp-tournament-manager/preview/` |

### 一般流程

1. 在 `develop` 分支開發新功能、修正
2. **升版**（見下節）：`patch` 給 preview、`minor`/`major` 視變更幅度
3. `npm run deploy:preview` → 在 `/preview/` 試用、給人測試
4. 確認沒問題 → `develop` 合併進 `master`
5. 切到 `master`，`npm run deploy` → 推上正式版

### 版本升級

每次 deploy 前先升版，讓 build 進去的 `package.json` 版本號跟「關於」彈窗顯示的版號對得上。

```bash
cd tournament-menager
npm version patch   # 1.1.0 → 1.1.1
```

⚠ **Gotcha**：因為 `package.json` 在子目錄 `tournament-menager/` 而非 git root，`npm version` 只會更新檔案、**不會自動建立 commit 與 tag**（但 `postversion` 仍會跑 `git push`，把現有未推的 commit 推上去，誤以為成功）。需手動補上：

```bash
git add tournament-menager/package.json tournament-menager/package-lock.json
git commit -m "chore: bump version to X.Y.Z"
git tag vX.Y.Z
git push && git push --tags
```

之後再跑 `npm run deploy:preview` 或 `npm run deploy`。

### 注意事項

- **共享 localStorage**：兩個版本是同一個 origin（`https://ritaweng.github.io`），瀏覽器的 localStorage 會互通。測試 preview 時建議使用**無痕視窗**或不同瀏覽器，避免動到正式版的比賽狀態。
- **不要並行部署**：避免 `deploy` 和 `deploy:preview` 同時跑，可能造成 `gh-pages` 分支推送衝突。
- **不要省略 `-e preview`**：直接跑 `gh-pages -d dist` 預設會清空整個 `gh-pages` 分支（含 `/preview/`）；`deploy:preview` script 已綁好參數，照 npm script 跑即可。
- **快取延遲**：GitHub Pages 部署後可能 1–10 分鐘才看到新版本，必要時用 Ctrl+F5 強制重整。

## 回歸測試

每次改版（尤其改動到抓對 / 算分邏輯）都應跑一次回歸測試。

```bash
cd tournament-menager
npm run test:regression
# 或：node tests/regression/replay_excel.js（從專案根目錄）
```

測試以歷年比賽 Excel（`tests/fixtures/`）為 ground truth，逐輪把實際結果餵回演算法、比對程式產出的對局是否與真實賽事 100% 吻合。回傳碼：`0` 全通過、`1` 有差異、`2` 找不到 fixture。

**Fixture 為去識別化版本**：`tests/fixtures/` 下的 Excel 已將學校名稱替換為 `學校NN`（保留 A/B/C 隊伍後綴），其餘數值欄位完全保留。`.gitignore` 對該目錄設了例外放行，clone 後即可直接跑測試。新增其他歷史比賽 fixture 的去識別化規則與步驟見 [`tests/README.md`](tests/README.md)。

**演算法共用同一份程式碼**：`tournament-menager/src/lib/swissPairing.js` 同時被 React 元件與此測試腳本 import，動了演算法就一定會被測試覆蓋到，不會發生「測試還在跑舊邏輯」的情形。

## 線上成績回報（選用）

讓各桌裁判用手機直接回報該桌勝負，主控端即時彙整，取代「裁判舉手 → 主控手動點選」。
**這是選用功能**：不建立線上賽事時，系統行為與純前端版本完全相同；後端臨時不可用時
可隨時退回手動點選，比賽不中斷。完整規格（架構、安全、API、分階段計劃）見
[`docs/online-score-reporting-plan.md`](docs/online-score-reporting-plan.md)，後端說明見
[`backend/README.md`](backend/README.md)。

> **後端已於 2026-07-07 部署上線**。正式網址、驗收與部署紀錄、Cloudflare 帳號資訊、
> 每次比賽的操作、重新部署方式、免費額度預算，都在
> [`docs/online-score-reporting-ops.md`](docs/online-score-reporting-ops.md)（維運手冊）。

### 定位

- 主控端維持**唯一權威**：賽事狀態仍在主控機 localStorage、正式紀錄仍是賽後 Excel/JSON。
- 後端只是**成績中繼站**：保管當場配對／裁判回報／輪次鎖定／稽核，賽後即刪（另有 7 天 retention）。
  後端**完全不懂瑞士制**——不抓對、不算分、不排名；`swissPairing.js` 一行未動。

### 比賽日流程

1. 主控端「線上回報」面板 →「建立線上賽事」（填後端網址）→「列印 QR 卡」，**QR 卡交計分台保管**。
2. 裁判報到時在計分台當面掃碼（token 進手機、卡收回）；面板「各桌狀態」可看誰上線了。
3. 每輪抓對後按「發佈桌次」→ 裁判手機數秒內自動顯示本桌對局 → 裁判點勝方、確認、送出。
4. 主控端輪詢自動收成績，桌卡標「裁判」來源；裁判更正會**醒目警示需操作者確認**才採計。
5. 到齊後照常「算分」→ 該輪自動鎖定，裁判端顯示「已鎖定」。
6. 賽後「結束線上賽事」→ 伺服器資料立即刪除、所有 QR 失效。

### 安全重點

QR 卡全程由計分台保管、當面掃碼（token 不上桌）；token 只存 SHA-256 雜湊、綁桌次；
已鎖定輪次伺服器拒收提交；重複提交 idempotent、更正記 revision；換裝置以**軟性偵測**
（device_id 變化入稽核＋主控端 ⚠ 標示）留痕；CORS allowlist + rate limit（格式正確 token
的 IP 桶放寬 10 倍以容納場地共用 Wi-Fi，未認證流量維持窄桶）。詳見規劃文件第 4 節。

### 後端測試

```bash
cd backend && npm install && npm test
```

`npm test` 會 spawn 真實 `wrangler dev` + 本地 D1 打 HTTP，涵蓋越權被拒、鎖定拒收、
idempotent、錯誤 token 401、device_id 稽核、CORS、rate limit 等（28 項）。前端整合另有
Playwright 端到端演練（主控 + 2 支模擬手機，含斷網恢復、token 外洩偵測）。

## 瑞士制抓對機制 — 技術說明與修正紀錄

### 算法核心：分組回溯法（對應 VBA Sub VS）

程式採用與原始 VBA 系統相同的**分組回溯法**進行瑞士制配對，以確保和 Excel 手動記錄的賽果完全吻合。以下為完整的算法流程說明及歷次修正原因。

---

### 一、排序邏輯（generateSwissPairings 排序鍵）

每輪抓對前，選手依以下複合鍵排序（依優先序）：

| 優先順序 | 排序鍵 | 方向 | 說明 |
|---------|--------|------|------|
| 1 | 總分 | 降冪 | 分數高者排前 |
| 2 | 輪動平衡（Float Balance） | **升冪** | 被輪高次數多者排後，下輪較可能輪低 |
| 3 | 輔分一 | 降冪 | 遭遇對手總分較高者排前 |
| 4 | 輔分二 | 降冪 | 所負對手總分較高者排前 |
| 5 | 輔分三 | 降冪 | 直接對戰較強者排前 |
| 6 | 籤號 | 升冪 | 最終穩定排序 |

### 二、分組邏輯（Group Boundary Leakage）

**根因說明**

分組採步長為 2 的比較：位置 `i` 的分數只與位置 `i-2` 比較。當某分數組的選手人數為**奇數**時，最後一個位置（`groupNum[i]` 與 `groupNum[i+1]` 同組）會將下一分數組的第一名選手納入同一組。此行為稱為「邊界洩漏（boundary leakage）」，是瑞士制的正確設計：

```
例：排序後位置 0~14（score=2，共 15 人）、位置 15（score=1）
  i=14：getScore(14)=2 == getScore(12)=2 → 同組
         groupNum[14]=1, groupNum[15]=1   ← 位置 15（score=1）被納入組 1
  i=16：getScore(16)=1 ≠ getScore(14)=2 → 新組 2
```

位置 15 的低分選手被納入高分組配對，符合瑞士制「奇數組借人」規則，而非算法錯誤。

**驗證結果**
以 2025 南北區比賽 Excel 實際記錄逐輪驗證：北區 29 隊 × 5 輪（75 場）、南區 22 隊 × 4 輪（44 場），**配對吻合率 100%**，所有輔分亦與 Excel 完全一致。驗證腳本見 [`tests/regression/replay_excel.js`](tests/regression/replay_excel.js)（執行方式見「回歸測試」章節）。

### 三、輪動平衡（Float Balance / computeFloatBalance）

**根因說明**

早期版本未實作輪動平衡，導致高分組選手在多輪後持續對上低分對手，排序不公平。

**修正方式**

新增 `computeFloatBalance` 函數，遍歷所有已完成輪次：
- 對每場對局，比較**配對當時（本輪前）**各選手的分數
- 分數較高者被「輪低」（-1）；分數較低者被「輪高」（+1）；同分者不變
- 排序時 `floatBalance` 以升冪排列，使累積被輪高較多的選手排序靠後，下輪優先被安排對上同分段對手

**關鍵細節**：浮動平衡比較的是「本輪開始前的分數」（`rounds 0..r-1` 之和），而非當輪結果，因此必須先計算 `scoresBeforeRound` 再做比較。

### 四、輪空計分修正（commit `09b3465`）

**根因說明**

輪空（BYE）場次的選手在 `calculateScores` 中，原始版本未正確將 `winPoint` 寫入該輪 `score` 欄位，導致 `totalScore` 少算一勝。

**修正方式**

在 `calculateScores` 裡，當 `match.player2 === 0`（輪空）時，直接將 `player1Score = winPoint` 寫入玩家的 `rounds[round-1].score`，確保：
1. 輪空選手的 `totalScore` 正確累加勝分
2. 後續輔分計算時，輪空輪不計入 `auxScore1` / `auxScore2`（因 `opponent === 0`）

### 五、回溯與借人機制（Backtracking & ReCrawl）

組內搜尋時，若最低排名選手找不到合法對手（已交手過；若啟用同國檢查則含同國衝突），系統自動**回溯**（撤銷前一組配對，改試其他組合）。若整組皆回溯失敗，則進入 **ReCrawl**：從下一組借入前 2 人擴大本組，重新嘗試。若仍失敗則逐組往前退，直到找到可行解。

> 同國檢查（`allowSameCountry`）目前預設 **不啟用**（即不擋同國配對）。state、setter、`conflictsCountry()`、Excel `country` 欄讀取都保留在程式碼中，未來要做出 UI 開關時可直接接上。
